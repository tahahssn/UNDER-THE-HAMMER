# Live auction room re-wired to the real backend; player advancement and reconnect state still incomplete

Second-pass review. The prior pass (CHANGES_REQUESTED, 8 findings) flagged that the room targeted non-existent HTTP endpoints and subscribed to events Phase I never emits. Commit `6932c13` reworks the integration against the real contract: bids now go over the authoritative Socket.IO `bid:submit` message on the `/auctions` namespace and reconcile by idempotency key; initial state loads from `GET /api/v1/auctions/:id`, `/teams`, and `/squads/rules`; the real-time layer only subscribes to events the gateway actually broadcasts and advances the player by requesting a fresh `room:snapshot` on `player:sold`. The three v1 HIGH blockers are genuinely resolved, as are the increment-bracket, break-requirements, and next-break-stat MEDIUMs. Two gaps remain, both confirmed in code: the next player never appears live during an auction, and the snapshot reconcile throws away the leading-bid fields the snapshot carries.

**Watch for:** `selectPlayerManual`/`drawPlayerAutomatic` record a `PLAYER_INTRODUCED` event but broadcast no socket message, and the client's only advance trigger (`player:sold` → snapshot) fires before the host has picked the next player, so the next player never appears live (confirmed); `reconcileFromSnapshot` hardcodes `leadingTeam: null` and ignores the `highBidMinor`/`highBidTeamId` the snapshot provides, so after every reconnect and every `player:sold` snapshot the leading team disappears and the bid form suggests a minimum below the true leading amount (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

The bid lifecycle now reaches the real backend. `useBidPlacement` emits `bid:submit` with `{ auctionId, auctionPlayerId, auctionTeamId, amountMinor, idempotencyKey, stateVersion }` on the `/auctions` namespace socket, and the gateway echoes the idempotency key on `bid:accepted`/`bid:rejected`/`bid:error` so optimistic entries reconcile by key. This half of the integration is sound and matches the gateway handler and the broadcaster changes in the same commit.

Initial state loads from endpoints that exist. `useAuctionState` combines `GET /api/v1/auctions/:id` with `/teams` and `/squads/rules`, treats a 404 as a missing auction, and keeps transport failures distinct (status stays null, retry UI) so a flaky network no longer masquerades as "not a member." The membership gate is driven by the socket `room:join:error` instead of a fabricated 404.

Live player advancement does not work end-to-end. The frontend correctly stopped subscribing to the never-emitted `player:introduced`, but its replacement — re-snapshot on `player:sold` — captures state before the host selects the next player, and player selection itself broadcasts nothing. So once a player sells, the room sits on a stale/empty current player until a reconnect or reload. This is a cross-phase gap the commit message flags as a blocker; it still blocks the core "players introduced one by one" journey.

Reconnect loses the leading bid. The snapshot the backend sends carries `highBidMinor` and `highBidTeamId`, but `reconcileFromSnapshot` discards them and sets `leadingTeam: null`. The result: after a reconnect or any `player:sold` snapshot, the leading team vanishes from the UI and the bid form recomputes its minimum from the base price, presenting a bid below the real leading amount as valid.

The remaining items are lower-stakes: the break-cadence counter is a per-player local approximation, the form uses the product's default increment brackets rather than the room's configured ones, squad-requirement rows always render zero progress, and the form declares a `roomId` prop it never reads.

1. **Next player never advances live** — `selectPlayerManual`/`drawPlayerAutomatic` broadcast no socket event, and the client re-snapshots only on `player:sold` (before the next player is picked), so the active player goes stale until reconnect. Add a socket broadcast on player introduction in Phase I and have the client re-snapshot on it (cross-phase; the commit documents this as a blocker).
2. **Snapshot reconcile discards the leading bid** — `reconcileFromSnapshot` sets `leadingTeam: null` and ignores the snapshot's `highBidMinor`/`highBidTeamId`, so reconnect and every `player:sold` snapshot drop the leading team and let the form suggest a minimum below the true leading amount. 3. **Break cadence counter is a per-player approximation** — `bidsUntilBreak = 5 - (acceptedThisPlayer % 5)` resets on each new player because the bid feed clears per player, so it can diverge from the server's configurable/global cadence. Source the count from the backend or scope it explicitly (AGENTS.md §7 warns against silently assuming the counter scope).
4. **Room increment brackets not wired** — the form defaults to the product sample brackets; a room with host-configured brackets gets a mismatched preview (backend still authoritative). Fetch and pass the room's configured brackets.
5. **Squad-requirement rows show no progress** — `mapSquadRules` hardcodes `currentCount: 0` and `satisfied: false`, so the break overlay lists requirements but every row reads zero. Populate per-team progress or document that rows are static labels.
6. **Dead `roomId` prop on BidPlacementForm** — declared required but never read. Remove it or use it.

### Bid transport and reconciliation (resolved)

`useBidPlacement.submitBid` now emits over the socket:

```
socket.emit('bid:submit', {
  auctionId, auctionPlayerId, auctionTeamId: teamId,
  amountMinor: String(amountMinor), idempotencyKey, stateVersion,
});
```

The gateway `@SubscribeMessage('bid:submit')` reads exactly these fields, calls `auctionsService.submitBid(... BigInt(data.amountMinor) ...)`, and the broadcaster now echoes `idempotencyKey` (and `auctionPlayerId`) on `bid:accepted`/`bid:rejected`, plus the gateway echoes it on `bid:error`. `useAuctionRealTime` reconciles the optimistic pending entry by that key, and `useBidPlacement` surfaces a rejection as a `BidError` on the form. All four gateways share the `/auctions` namespace and the client socket connects to `/auctions`, so the message reaches `AuctionRoomGateway`. The no-retry-on-4xx intent is preserved by failing fast when the socket is disconnected. This resolves v1 HIGH-1.

### State fetch and membership gate (resolved)

`useAuctionState` fetches `/api/v1/auctions/:id` (matching `@Controller('v1/auctions')` behind the `api` prefix), then `/teams` and `/squads/rules` as graceful-degradation supplements. A 404 sets `status` so the page renders not-found; a thrown transport error keeps `status` null and shows the retry UI. The page's `notFound()` now triggers on `status === 404` or an authoritative `room:join:error` (`AUCTION_NOT_FOUND`/`NOT_ROOM_MEMBER`/`UNAUTHORIZED`), not on a fabricated missing endpoint. This resolves v1 HIGH-2.

### Real-time alignment and the player-advancement gap

The subscription list is now `bid:accepted`, `bid:rejected`, `player:sold`, `player:unsold`, `break:started`, `break:ended`, `room:snapshot`, `bid:error` — the handlers for `player:unsold` are harmless forward-compat since the backend does not emit it. The removal of the dead `player:introduced`/`squad:updated` subscriptions resolves v1 HIGH-3 as stated.

The functional consequence is not resolved, and it is now concretely traceable. `selectPlayerManual` and `drawPlayerAutomatic` do:

```
await this.eventStore.recordEvent(auctionId, 'PLAYER_INTRODUCED', {...})  // persisted, not broadcast
```

No gateway `emit`/broadcast accompanies player introduction. The client's mitigation advances the player by `socket.emit('auction:request-snapshot')` inside `handlePlayerSold`. But a snapshot requested at the instant a player sells reflects the state *before* the host selects the next player, so the returned `currentPlayer` is the just-sold player or null. When the host then introduces the next player, nothing reaches the client. In practice the active player freezes after each sale until a reconnect or reload re-runs the snapshot. The commit message flags this as a Phase I blocker ("a dedicated introduce broadcast should be added"), which is the right call — but the live auction's central loop does not function end-to-end until that broadcast exists and the client re-snapshots (or updates directly) on it.

### Snapshot reconcile drops the leading bid

The backend snapshot includes the leading bid:

```
// auction-snapshot.service.ts
highBidMinor: auction.highBidMinor,
highBidTeamId: auction.highBidTeamId,
teams: teamsWithBalances,
currentPlayer,
```

`reconcileFromSnapshot` maps `currentPlayer` and `teams` but ends every player map with `leadingTeam: null` and never reads `snap.highBidMinor`/`snap.highBidTeamId`. Two effects follow on every reconnect and every `player:sold` snapshot:

- `PlayerIntroduction` shows no leading team even when one exists server-side.
- The page derives `currentLeadingBid` from `leadingTeam`, so it becomes null, and `computeMinimumBid(null, basePrice)` returns the base price. The form then presents a bid at base price as valid even though the real leading amount is higher — the backend rejects it with `INVALID_INCREMENT`, surfacing an error the user could have been spared, and undermining the "resume bidding after reconnect" success criterion.

The fix is to map `highBidTeamId` (resolved to a team name via the `teams` array) and `highBidMinor` into `currentPlayer.leadingTeam`. One caveat worth verifying server-side: the repository notes high bid moved to `AuctionPlayer` and `updateHighBid` is now a no-op, yet the snapshot still reads `auction.highBidMinor`. If that column is stale/null, restoring it on the client is necessary but not sufficient — the snapshot should source the high bid from the active `AuctionPlayer`.

### Break cadence counter scope

`bidsUntilBreak = BREAK_AFTER_N_BIDS - (acceptedThisPlayer % BREAK_AFTER_N_BIDS)` where `acceptedThisPlayer` counts accepted bids in the current feed. Because `reconcileFromSnapshot` clears `bids` whenever the player changes, this counter restarts at each player and reflects per-player accepted bids, not a running or configurable cadence. AGENTS.md §7 explicitly says the break counter scope "must be configurable or explicitly resolved; do not silently assume." This is a client preview and the backend proposes the real break, but the displayed countdown can mislead. Sourcing the remaining count from the backend (or scoping it deliberately) would align it.

### Increment brackets default to the product sample

`BidPlacementForm` defaults `incrementBrackets` to `DEFAULT_INCREMENT_BRACKETS` (the AGENTS.md §7 sample tiers) and the page passes no room-specific brackets. Rooms are allowed to configure their own bid-increment brackets, so for a customized room the client's "next valid bid" preview can disagree with server validation. The money handling itself is correct — integer minor units (paisa) throughout, consistent between `computeMinimumBid` and `formatMoney`.

### Squad requirement rows are static

`mapSquadRules` builds each requirement with `currentCount: 0` and `satisfied: false` unconditionally. The break overlay therefore lists the configured requirements (resolving the v1 empty-array finding) but shows no per-team fulfillment on those rows. If progress is meant to come from elsewhere in `BreakScreen`, documenting that would help; otherwise the rows read as "0 / min" for every team mid-auction.

### Minor

`BidPlacementForm` declares `roomId` as a required prop and the page passes it, but the component never reads it — dead surface area. No correctness impact.

### What is solid

New code is TypeScript-strict with no `any` (the lone `any` lives in pre-existing Phase H `BreakScreen`). The optimistic-bid reconciliation keys cleanly off the idempotency key the gateway now echoes, and double-submit is guarded with an in-flight ref. `BidPlacementError` maps every Phase G rejection code the spec names to a title plus recovery suggestion and announces via `role="alert"`. `RealTimeStats` now shows bids-remaining-to-next-break with the spec's approaching colour change (warn ≤5, danger ≤2). `TeamStandings` is driven entirely by the `teams` prop with a 1/2/3/4-column responsive grid and an initials fallback — no eight-team assumption. Keyboard support (Enter submit, Escape clear), `focus-visible` outlines, and `motion-safe:` transitions are present. The membership-gate reasoning (client JWT, no server-readable cookie) is documented at the top of the page.
